## 1.3.0 — оптимизация

### Фронтенд

- **−206 КБ JavaScript (−64 КБ gzip) на странице входа.** Material UI (+ Emotion) использовался только на страницах
  входа и регистрации — первой странице для нового посетителя. Заменён лёгкими компонентами `shared/ui/Form`
  с тем же API. Из зависимостей удалены `@mui/material`, `@mui/icons-material`, `@emotion/*`, а также
  неиспользуемые `axios` и `sass` — `npm install` заметно быстрее. Общий объём JS: 704 → 490 КБ.
- **Главная: 1 запрос вместо 2.** Ради счётчиков «N товаров» загружался весь каталог с изображениями;
  теперь количество приходит в `GET /api/Categories` (`ProductCount`).
- **Страница товара: запросы параллельно.** Товар, отзывы и характеристики грузились тремя последовательными
  запросами. Теперь товар и отзывы — параллельно, а характеристики берутся из ответа товара (отдельный запрос
  только как запасной вариант). Убран параметр-«антикеш» у отзывов.
- **Профиль:** корзина и заказы загружаются параллельно.
- **Без лишних CORS-preflight.** `Content-Type: application/json` отправлялся и в GET-запросах — из-за этого
  браузер перед каждым запросом к API слал дополнительный OPTIONS. Теперь заголовок только у запросов с телом.
- **Изображения:** `loading="lazy"` и `decoding="async"` в списках (карточки, корзина, оформление),
  `fetchPriority="high"` у главного фото товара.
- **Анимации без перерисовок.** Бесконечные анимации `background-position` и `box-shadow` (перерисовка каждый
  кадр, в т.ч. внутри шапки с размытием) заменены на `transform`/`opacity`, которые выполняются на GPU;
  `background-attachment: fixed` — на фиксированный слой; убран `backdrop-filter` с повторяющихся элементов;
  3D-наклон карточек обновляется не чаще одного раза за кадр.

### Бэкенд

- `GET /api/Categories` возвращает `ProductCount` — один `GROUP BY` по активным товарам.
- **Output cache** для карточки товара `GET /api/Products/{id}`, поиска и характеристик товара (30 с,
  сбрасывается при изменениях каталога). Ответ администратору о снятом с продажи товаре в общий кеш не попадает.
- **Поиск по индексу.** Миграция `20261024120000_SearchTrigramIndexes`: триграммные GIN-индексы (`pg_trgm`)
  для `ILIKE '%…%'` по названию и описанию — раньше каждый поиск читал всю таблицу. Если прав на
  `CREATE EXTENSION` нет, миграция не падает, поиск работает как раньше.
- **Изображения товаров: 6,4 → 3,1 МБ.** Уменьшены до 1000 px по длинной стороне и пережаты в том же формате
  и с теми же именами (одно фото было 4032×3024 и 1,5 МБ при показе в карточке ~300 px).

### Тесты

- Фронтенд: 545 (+4): один запрос на главной, характеристики без отдельного запроса, параллельная загрузка
  товара и отзывов, GET без Content-Type.
- Бэкенд: +2 — счётчики товаров в обработчике категорий и в репозитории.

### Анимации

Появление страниц и карточек (каскадом), 3D-наклон категорий, блики на кнопках и картинках, «парящее» фото

## 1.2.0

### Исправленные ошибки и уязвимости

**Данные и целостность**

- **Удаление из коллекций агрегатов не сохранялось.** Репозитории загружали агрегаты без отслеживания
  (глобальный `NoTracking`) и сохраняли их через `Update()` на отсоединённом графе. В итоге удаление товара
  из корзины, обнуление количества, удаление изображения или характеристики товара в БД не попадало,
  а связанные сущности (товар, бренд, пользователь у отзыва) перезаписывались устаревшими значениями.
  Теперь агрегаты для изменения загружаются с `AsTracking()`, а `Update()` вызывается только для
  отсоединённых объектов (`RepositoryExtensions.AttachForUpdate`). Добавлены регрессионные тесты
  «один запрос — один DbContext».
- **Контакты покупателя терялись.** Имя, фамилия, email и телефон из формы оформления принимались API,
  но нигде не сохранялись. Теперь это value object `CustomerContact` с валидацией; в БД хранится
  зашифрованным AES-GCM (уже существовавший, но неиспользуемый `EncryptionService`).
- **Можно было купить снятый с продажи товар**, если он остался в корзине; позиции без товара молча
  выкидывались из заказа. Теперь — явная ошибка до любых изменений.
- **Создание товара с несуществующим брендом/категорией/типом** приводило к нарушению FK и ответу 500.
  Теперь — проверка и понятная ошибка 400.
- **Частичное обновление товара**: при некорректной цене название уже успевало измениться. Валидация
  перенесена до изменений.

**Безопасность**

- **JWT оставался действительным сутки** после смены пароля, смены роли (в т.ч. понижения админа) или
  удаления пользователя. Добавлена метка безопасности (`User.SecurityStamp`): попадает в токен (claim
  `sstamp`) и сверяется на каждом запросе (`UserSessionValidator`, кеш 30 с, сброс при изменении пользователя).
- **Новый пароль при смене не проверялся** (можно было сменить на `1`). Единая `PasswordPolicy`:
  минимум 8 символов, буква и цифра, не более 72 байт (лимит BCrypt). Новый пароль должен отличаться от старого.
- **Перебор логинов по времени ответа**: для несуществующего пользователя теперь тоже выполняется проверка
  BCrypt-хеша; ошибка формата логина при входе не раскрывается.
- Администратор не может изменить собственную роль, удалить себя и понизить последнего администратора.
- Ошибки доступа отдают 403, отсутствие объекта — 404, конкурентные конфликты и дубли — 409
  (раньше всё было 400 или 500).
- Глобальный лимит запросов на IP, заголовки безопасности (`X-Content-Type-Options`, `X-Frame-Options`, ...).
- `docker-compose.yml`: пароль PostgreSQL был зашит (`root`), а бэкенд подключался с `${POSTGRES_PASSWORD}` —
  при любом другом значении в `.env` бэкенд не мог подключиться. Порт БД теперь слушает только `127.0.0.1`.

**Фронтенд**

- Текст ошибки сервера терялся (`HTTP 400` вместо «Неверное имя пользователя или пароль»): `httpClient`
  теперь берёт сообщение из ответа, тело читается через `clone()` (старый код, читающий `error.response.json()`, работает).
- При 401 вызывался `localStorage.clear()` — стирались кэш каталога и прочие настройки. Теперь удаляются только ключи авторизации.
- Кэш категории сохранял только первые 5 товаров — при возврате на страницу на мгновение показывался обрезанный список.
- `alert()` при ошибке добавления в корзину заменён уведомлением с текстом сервера.
- После смены пароля пользователь больше не разлогинивается — сохраняется новый токен.

### Новые возможности

- **Склад.** `Product.StockQuantity` (токен оптимистичной блокировки — склад не уходит в минус при
  параллельных заказах), резерв при оформлении заказа, возврат при отмене (только для заказов с резервом),
  проверка остатка при добавлении в корзину. Админ: `PUT /api/Products/{id}/stock`, вкладка «Склад».
- **Каталог с серверной пагинацией**: `GET /api/Products/paged` — фильтры по категории, типу, брендам,
  цене, тексту, наличию; сортировка; страница. Пять почти одинаковых страниц категорий (~200 строк каждая)
  заменены общим виджетом `CategoryCatalog`; ввод цены — с debounce.
- **Избранное**: API `/api/Wishlist`, сердечко на карточке и странице товара, страница «Избранное», счётчик в шапке.
- **Модерация отзывов**: `GET /api/Reviews/pending`, `PUT /api/Reviews/{id}/reject`, вкладка «Отзывы»
  в админке; `Reviews:RequireModeration` включает премодерацию (изменённый автором отзыв возвращается на проверку).
  Распределение оценок 1–5 в ответе отзывов товара.
- **Управление товаром**: полное редактирование (`PUT /api/Products/{id}`), возврат в продажу (`POST /{id}/activate`).
- **Админка**: заказы постранично с фильтром по статусу, на дашборде — «Нет в наличии» и «Отзывов на модерации».
- **Health-checks**: `/health/live`, `/health/ready` (проверка БД); Docker HEALTHCHECK использует `/health/live`.

### Оптимизация

- Админский список заказов: имена пользователей одним запросом вместо N+1, пагинация в БД.
- `GET /api/Products?limit=N` — лимит применяется в БД, а не после загрузки всего каталога.
- Output cache (30 с) для публичных списков каталога, в том числе для авторизованных пользователей;
  сбрасывается при изменениях каталога и остатков (`[EvictCatalogCache]`).
- Индекс `(CategoryId, IsActive, Price)` для каталога; кеширование изображений в браузере (`Cache-Control`).
- Убран лишний запрос очистки корзины после оформления заказа (сервер очищает её в той же транзакции).
- Brotli/Gzip — уровень `Fastest`.

### Архитектура

- `IUnitOfWork` (реализует `ApplicationDbContext`) для сценариев, затрагивающих несколько агрегатов
  (отмена заказа + возврат на склад — одна транзакция).
- Ошибки EF (`DbUpdateConcurrencyException`, нарушение уникальности) переводятся в доменный
  `ConflictException` внутри инфраструктуры — веб-слой не зависит от EF Core.
- Общий `ApiControllerBase` вместо копии `GetCurrentUserId` в каждом контроллере; единый `OrderMapper`.
- `PagedResult<T>`, `ProductQuery`, `NotFoundException` / `ForbiddenException` / `ConflictException` в домене.

### Миграция `20261021120000_StockWishlistSecurity`

- `Products.StockQuantity` (существующим товарам выставляется 10 шт.), индекс по цене;
- `Users.SecurityStamp` (каждому пользователю — случайная метка);
- `Orders.CustomerContact` (зашифрованный JSON), `Orders.StockReserved`;
- таблица `WishlistItems`.

> После обновления ранее выданные токены (без метки безопасности) недействительны — пользователям нужно войти заново.

### Важно проверить

Миграция и снимок модели написаны вручную (в среде, где готовилось обновление, не было доступа к NuGet).
Предупреждение EF о расхождении модели и миграций переведено в лог, чтобы приложение не падало при старте.
Проверьте синхронизацию командой из раздела «Тесты» README — новая миграция должна получиться пустой.
